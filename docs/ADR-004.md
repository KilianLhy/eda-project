# ADR-004 : Disruption #1 - Cross-cutting via ports + domain events

## Statut

Accepte

## Contexte

La disruption #1 ajoute des besoins transverses :
- authentification JWT (future migration vers SSO)
- temps reel scope par projet
- notifications multi-canaux avec preferences utilisateur
- audit trail sur les ecritures Task/Project
- CLI admin sans duplication de logique metier

Le risque principal est de coupler ces besoins techniques au coeur metier (`ProjectService`, `TaskService`).

## Decision

Nous conservons les services metier comme orchestrateurs de cas d'usage et nous ajoutons les capacites transverses par adaptateurs :

1. Auth
- `AuthController` + `AuthService` + `JwtAuthGuard`
- Les controllers metier lisent `CurrentUser` depuis le token.
- Les services metier reçoivent seulement `actorId` (pas de dependance JWT).

2. Temps reel
- `TaskService` publie `task.moved` comme avant.
- `TaskMovedRealtimeHandler` consomme l'evenement et appelle un port `RealtimeBroadcasterPort`.
- `TaskRealtimeGateway` (Socket.IO) implemente ce port et diffuse par room `project:<id>`.

3. Notifications
- `TaskNotificationHandler` consomme `task.assigned` et `task.moved`.
- Les canaux sont des adaptateurs (`EmailNotificationChannel`, `InAppNotificationChannel`) selectionnes via preferences.
- Ajouter Slack/Teams/SMS = nouveau channel + enregistrement DI, sans toucher aux services metier.

4. Audit
- `AuditLogHandler` consomme les evenements d'ecriture (`project.created`, `member.added`, `task.created`, `task.moved`, `task.assigned`) et persiste dans `AuditLog`.
- Les services metier ne contiennent aucune logique de log technique.

5. CLI
- `src/cli/admin.cli.ts` instancie le contexte Nest et appelle `ProjectService` / `TaskService`.
- Pas de duplication des regles metier : la CLI reutilise les memes cas d'usage que l'API.

## Alternatives envisagees

| Alternative | Raison du rejet |
|-------------|-----------------|
| Injecter WebSocket/Notification/Audit directement dans `TaskService` | Couplage fort, faible evolutivite, impact important en cas de changement technique. |
| Ajouter une logique dediee CLI hors Nest | Duplication du metier et divergence de comportement API vs CLI. |
| Coder l'audit dans chaque controller | Pollution des endpoints, risques d'oubli, faible maintenabilite. |

## Consequences

### Positives
- Changement du mecanisme auth/realtime/notification/audit possible sans re-ecrire les regles metier.
- Extensibilite naturelle des canaux de notification.
- Coherence entre API REST et CLI grace au meme service applicatif.

### Compromis assumes (MVP livraison)
- JWT simple local (pas de refresh token, pas de revocation).
- Envoi email simule en console.
- Realtime non authentifie au niveau socket (room par projet cote client).
- Audit stocke en base applicative (pas de backend d'audit dedie).

### Evolution production
- Remplacer JWT local par OIDC/SSO via nouvel adaptateur d'authentification.
- Remplacer `InMemoryEventBus` par bus durable + outbox.
- Authentifier les sockets et valider l'acces projet cote serveur.
- Externaliser emails/notifications/audit vers des services dedies.
